## 摘要
检索可以识别出一条可能重要的过往轨迹，但它并未规定在用户、实体、约束条件或环境状态发生变化之后，执行中的智能体应当如何使用该轨迹。我们将这一检索后的重用步骤识别为长时程轨迹记忆的一个独特瓶颈，并提出一个评估框架，该框架在保持候选检索、目标状态、模型、解码和工具预算固定的同时，改变提供给智能体的支持。我们用查询条件重用（QCR）实例化该框架，这是一种刻意简化的目标绑定注记，记录了可重用的过程、需要恢复的绑定、适用条件和验证要求。QCR用于检验重用假设，而非主张一种普遍优先的记忆格式。在WebArena、WorkArena和AppWorld中的2,391个目标实例上，QCR达到了62.3%的平均成功率，比完整轨迹高出10.7个百分点，同时减少了48.9%的在线令牌使用量。摘要重排序为94.8%的目标选择了可重用的记忆，使最终任务成功率与一个理想的可重用选择器相差在1.8个百分点之内。按轨迹长度和源-目标绑定变化进行的分析表明，随着轨迹变长或源特定值改变，直接轨迹注入会失去很大效用，而目标绑定支持则保持更大比例的测得增益。由此产生的框架将检索质量与将检索到的经验转化为对新任务安全、有用支持的问题分离开来。

## Abstract
Retrieval can identify a past trajectory that may matter, yet it does not specify how an acting agent should use that trajectory after users, entities, constraints, or environment state have changed. We identify this post-retrieval reuse step as a distinct bottleneck for long-horizon trajectory memory and formulate an evaluation framework that holds candidate retrieval, target state, model, decoding, and tool budget fixed while varying the support delivered to the agent. We instantiate the framework with query-conditioned reuse (QCR), a deliberately simple target-bound note that records a reusable procedure, bindings to recover, applicability conditions, and verification requirements. QCR serves to test the reuse hypothesis rather than to claim a universally preferred memory format. Across 2,391 target instances in WebArena, WorkArena, and AppWorld, QCR reaches 62.3% average Success, 10.7 points above Full Trajectory, while using 48.9% fewer online tokens. Summary reranking selects a reusable memory for 94.8% of targets, placing end-task Success within 1.8 points of an oracle reusable selector. Analyses by trajectory length and source--target binding shift show that direct trajectory injection loses much of its utility as traces grow longer or source-specific values change, whereas target-bound support preserves a larger share of the measured gain. The resulting framework separates retrieval quality from the problem of turning retrieved experience into safe, useful support for a new task.

## 一、核心问题与整体含义（研究动机与背景）

* **核心痛点**：现有智能体记忆系统在“检索”环节已取得长足进步（如 MemGPT、MemoryBank、HippoRAG 等），但**检索到一条历史轨迹 ≠ 智能体知道如何在新任务中正确使用它**。当用户、实体、约束条件或环境状态发生变化后，直接照搬旧轨迹往往会导致错误。
* **关键洞察**：随着记忆单元从“短事实”→“片段”→“长轨迹”不断变长，**瓶颈从“检索”（能不能找到）转移到“复用”（找到后如何用）**。对于短记忆，检索到即等于可用；但对于长时程轨迹，其中包含大量源任务特有的用户、对象、路径、日期等绑定信息（binding），不加区分地注入会引入过期绑定（stale binding），误导智能体。
* **研究定位**：论文主张将“检索质量”与“检索后经验转化为安全、有用的任务支持”**分离为两个独立问题**，并提出一个刻意简化的目标条件化复用（QCR）方法来检验“复用假设”，而非宣称一种普适最优的记忆格式。

## 二、方法论：核心思想、关键技术细节与流程

### 2.1 总体思想
在检索完成之后、目标智能体执行之前，插入一个**“目标条件化支持构造”步骤**：不是直接把原始轨迹丢给智能体，而是生成一份简洁的、**绑定到当前目标**的复用笔记，告诉智能体“哪些流程可复用、哪些值必须重新获取、何时应放弃复用、如何验证”。

### 2.2 QCR 支持笔记的四字段结构
| 字段 | 内容 | 目的 |
|---|---|---|
| 工作流不变式（workflow invariant） | 目标仍然需要的动作模式，如“检查-验证-修改-确认” | 保留可迁移的操作顺序与决策规则 |
| 需重新获取的绑定（bindings to re-obtain） | 源轨迹中出现的用户、路径、日期、对象 ID 等，但目标值未知 | 阻止直接复制源值，要求从目标观测中重新获取 |
| 适用性条件（applicability conditions） | 源前提条件、约束、分支条件 | 当目标状态违反前提时允许放弃复用 |
| 验证防护栏（verification guardrail） | 源任务的完成校验方式 | 要求目标侧执行等价验证后才结束 |

### 2.3 评估框架与流程（三个阶段的严格边界）

1. **离线记忆库构建**：用 DeepSeek-V4-Pro 在 WebArena、WorkArena、AppWorld 上执行源任务，通过各自环境校验器后，收集 623 条已验证轨迹，构成一个**跨环境的统一冻结混合记忆库**（不按环境分区）。
2. **绑定感知的目标构造**：对每条源轨迹生成最多 4 个目标变体，保留工作流但替换 1 至多个绑定值，分为 None / Small / Medium / Large 四个绑定偏移等级，共产生 2,391 个有效目标任务。
3. **在线评估流程**：
   * 固定嵌入检索器（BGE-M3）从统一库中返回共享 top-5 候选集合；
   * 轻量级排序器（DeepSeek-V4-Pro）从 top-5 中选出一条记录；
   * 四个对比条件（No Memory / Generic Summary / Full Trajectory / QCR）**共享完全相同的缓存候选集、选中轨迹、目标查询、初始观测、模型、解码配置、工具预算**，仅改变“所选经验的表示与使用方式”。

### 2.4 信息边界（信息隔离）
* 检索器只能访问源指令与轨迹描述符，**不接触环境标签、任务 ID、源-目标配对关系和校验器诊断**。
* QCR 只能读取选中轨迹 + 目标查询 + 初始观测，**不能私有调用环境或替换候选选择**。
* 源-目标配对关系仅作为密封审计元数据，不进入任何提示。

## 六、主要结论与发现

1. **QCR 综合表现最優**：平均 Success 62.3%，相比 Full Trajectory 高 10.7 个百分点，相比 No Memory 高约 23.9 个百分点；API 调用最少（16.7 次）；在线 token 仅 9.4k，比 Full Trajectory 的 18.4k **减少 48.9%**。
2. **重排序对选择有效**：top-5 覆盖率高（paired 95.6%、reusable 97.8%），但检索器 top-1 配对精度仅 78.9%；经摘要重排序后，最终可复用记忆选择精度升至 94.8%，端任务成功率（62.3%）与 oracle 可复用选择器（64.1%）仅差 1.8 个百分点。
3. **轨迹越长，直接注入效用越差**：Full Trajectory 在 Short 组相对 No Memory 增益 +18.4 点，在 Very Long 组坍塌至 +2.9 点（保留短轨迹效用的 15.8%）；QCR 在 Very Long 组仍保持 +13.2 点（保留 60.3%）。
4. **绑定偏移越大，直接复用越危险**：Full Trajectory 在无偏移时增益 +26.9，大偏移下跌至 +2.2（保留 8.2%）；QCR 从 +29.6 降至 +20.1（保留 67.9%）。大偏移下 Full Trajectory 的 stale-binding 错误率达 46.9%，QCR 仅 10.9%；正确重绑定率从 31.7% 提升至 77.8%。
5. **检索与复用是两个独立瓶颈**：即使检索质量已经很高，后检索阶段处理方式仍然显著影响端任务结果。

## 七、优点与亮点

* **问题定义清晰**：首次明确将“检索后复用”从记忆管线中独立出来，作为可单独评估的瓶颈，并给出了严格的评估边界。
* **评估协议严谨**：固定候选集、选中轨迹、模型、解码、工具预算、初始状态，只改变记忆表示方式；在线 token 核算细致（避免将 API 输入重复计数），支持成本单独列出，防止“虚假的免费收益”。
* **统一跨环境记忆库**：打破环境隔离，允许跨环境检索与迁移，更贴近真实部署场景。
* **绑定感知的目标构造**：构建了 2,391 个受控源-目标变体，形成可量化、可审计的绑定偏移梯度测量体系。
* **诊断与端到端分离**：既报检索覆盖率、选择精度，又报端到端 Success 与成本，清楚地指出选择瓶颈与复用瓶颈各自的贡献。
* **理念可以落地**：QCR 不要求改造存储或检索，只增加一个轻量后处理步骤，实用性强；支持“全量记录留在库中、提示词只放目标绑定摘要”的工程建议。

## 八、不足与局限

* **实验覆盖有限**：仅覆盖成功轨迹，未考察部分失败、自然出现的重复任务、多记忆组合、开放式的长期记忆获取；这些场景可能改变可复用流程与需要恢复的状态结构。
* **单模型依赖性**：仅使用 DeepSeek-V4-Pro，结论在 GPT、Claude、Gemini 等模型上是否成立尚需验证。
* **受控偏移与真实漂移的差距**：绑定重写是人工构造的受控梯度，真实部署中的状态漂移往往更复杂、更具偶发性。
* **单条记忆选择**：当前设定每次只选择一条记忆注入，未探索多轨迹融合或跨条交叉验证的策略。
* **安全性度量空白**：只测量校验器确认的完成率，未系统测量不可逆副作用、策略违规或由复用轨迹引发的新风险。
* **字段归因不清**：QCR 框架的四个字段是一个整体设计，实验未单独消融每个字段的独立贡献，无法确定哪个字段对收益贡献最大。
* **长度/绑定偏移分析是相关性而非因果**：按照长度分组后，各组间无记忆基线难度差异很大（Short 组 55.2% vs Very Long 组 18.9%），因此表 2/表 3 的结果是“关联”而非可证明的因果效应。
* **受控环境的外推风险**：三个基准仍属于模拟环境，距离真实互联网规模下的轨迹记忆应用仍有距离；token 节省也不应被解读为“越少越好”，安全敏感任务可能必须保留额外的检查动作。
