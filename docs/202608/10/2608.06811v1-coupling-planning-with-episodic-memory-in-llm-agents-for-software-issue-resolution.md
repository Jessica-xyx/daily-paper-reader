## 摘要
使用大型语言模型（LLM）智能体解决真实软件问题是一个漫长的修复过程，通常涉及数十到数百个步骤，涵盖探索、假设、实现和验证。成功既依赖于基础模型的局部推理，也依赖于智能体维护不断发展的计划并跨阶段记住观察结果的能力。现有的仓库级智能体通常孤立地强化规划或记忆，使得长轨迹容易受到过时证据、重复失败的编辑以及从智能体自身声明而非执行证据推断验证的影响。我们提出了PMCoder，一个将分层阶段规划器与情景记忆相结合的问题解决智能体。这种耦合是双向的：当前计划阶段调节记忆检索，而从记忆派生的轨迹统计信息为卡住检测和重新规划提供依据。当可用时，问题复现判定会基于执行证据而非自我报告的完成情况来确认验证进度。在SWE-bench Verified上，PMCoder比匹配的基线平均多解决25个案例（+5.0个百分点），即使在没有触发复现门控的情况下，收益依然存在。进一步的Verified-500评估显示，在Claude Haiku 4.5、DeepSeek-V4-Flash和OpenHands移植上，也呈现相同的积极趋势，至少多解决了14个案例（+2.8个百分点）。此外，在TerminalWorld官方样本上的评估表明，这种规划-记忆基础可以迁移到问题报告之外。消融和轨迹分析显示了收益来源：规划与记忆的耦合优于单独使用任一组件，并减少了重复失败的操作、空补丁退出和上下文窗口耗尽。

## Abstract
Resolving a real software issue with a large language model (LLM) agent is a long repair episode, often tens to hundreds of steps spanning exploration, hypothesis, implementation, and verification. Success depends on both the base model's local reasoning and the agent's ability to maintain an evolving plan and remember observations across phases. Existing repository-level agents typically strengthen planning or memory in isolation, leaving long trajectories vulnerable to stale evidence, repeated failed edits, and verification inferred from the agent's own claims instead of execution evidence. We present PMCoder, an issue-resolution agent that couples a hierarchical phase planner with episodic memory. The coupling is bidirectional: the current plan phase conditions memory retrieval, while memory-derived trajectory statistics inform stuck detection and replanning. When available, issue-reproduction verdicts ground verification progress in execution evidence rather than self-reported completion. On SWE-bench Verified, PMCoder resolves an average of $25$ more cases ($+5.0$pp) than a harness-matched baseline, with gains persisting even where the reproduction gate never fires. Further Verified-500 evaluations show the same positive direction across Claude Haiku 4.5, DeepSeek-V4-Flash, and an OpenHands port, with at least $14$ additional resolved cases ($+2.8$pp). Separately, evaluation on TerminalWorld's official sample suggests that the plan-memory substrate transfers beyond issue reports. Ablation and trajectory analyses show where the gains come from: coupling planning and memory outperforms either component alone and reduces repeated failed actions, empty-patch exits, and context-window exhaustion.

## 1. 核心问题与研究动机

- **背景**：用 LLM 智能体解决真实软件 issue 是一个长周期修复过程，通常需要数十至数百步，涵盖探索（exploration）、假设（hypothesis）、实现（implementation）与验证（verification）四个阶段。成功不仅取决于基础模型的局部推理能力，还取决于智能体能否维护一个不断演进的计划，并跨阶段记住关键观察。
- **问题**：现有仓库级智能体（如 SWE-agent、AutoCodeRover、SWE-Exp 等）往往**孤立地强化规划或记忆**，导致长轨迹中三类典型失败：
  - 过时证据残留（早期观察在后期失去可检索性）；
  - 重复失败的编辑（同一错误操作反复执行）；
  - 验证过程依赖模型**自我声称**而非执行证据（如自写 always-pass 测试、伪造成功打印）。
- **核心缺口**：规划与记忆之间缺乏**双向耦合**——当前计划阶段应决定哪些历史信息仍然相关，而累积经验应决定计划何时需要改变。已有工作（如 Shen et al. 的 subtask-aligned memory）只实现了 plan→memory 单向对齐，没有让 memory 驱动 replanning。
- **研究意义**：首次提出将规划与情景记忆作为**双向耦合的状态系统**用于仓库级软件修复，并用执行证据锚定共享计划-记忆状态的推进，属于机制层面的研究，而非排行榜竞争。

## 2. 方法论（PMCoder）

PMCoder 在标准 observe–act 循环之上增加了两个耦合的状态结构，保持原有工具调用接口不变。

### 2.1 核心思想
- **双向耦合**：计划状态条件化记忆检索（plan→memory），记忆派生的轨迹统计驱动卡住检测与重规划（memory→plan）。
- **执行接地（Execution Grounding）**：用问题复现判定（issue-reproduction verdict）替代自我声称的验证信号，锚定计划状态的推进。

### 2.2 分层阶段规划器（Hierarchical Phase Planner）
- **计划状态**：确定性状态机，含四个按标量排序的阶段（EXPLORATION → HYPOTHESIS → IMPLEMENTATION → VERIFICATION）加一个处于排序之外的 BACKTRACK 恢复事件。
- **子任务分解**：每个 episode 仅一次 LLM 调用，将 issue 分解为带目标阶段标签的 typed sub-tasks；解析失败时回退到固定骨架。
- **阶段检测**：每步使用零成本的规则检测器，依据 shell 命令与模型推理文本归类；四条信号类别按有序规则匹配（文件检查→探索；诊断命令→假设；文件修改→实现；测试执行→验证）。
- **卡住检测与重规划**：最小步数限制后，检测持续非零返回码、单文件编辑次数过多、读操作饱和、归一化动作重复超阈值等信号；触发后标记当前子任务失败，压入恢复子任务（含 revert-then-refix 模板），并设冷却与深度上限防止重规划风暴。
- **导出信号**：每步导出当前阶段、活动子任务、进度计数、最常修改文件、分阶段 token 预算及回溯标志，用于条件化记忆检索。

### 2.3 情景记忆（Episodic Memory）
- **记忆节点**：每条消息镜像为节点，存文本 + 结构化元数据（角色、recency 标识、压缩内容、摘要、前置命令是否编辑文件、涉及哪些文件）。编辑元数据从**实际执行的命令**中读取，而非模型声称。
- **有预算的 MMR 检索**：固定核心（任务陈述、最近尾部、锚节点）+ 束搜索按边际增益选择工作集：

  g(v) = λ·rel(v) − (1−λ)·max sim(v,u)（u∈S，已选集）

  rel(v) = wc·lex(v) + wg·graph(v)

  其中 lex 为 IDF 加权的词法分数，graph 为代码结构图（同文件共现、Python 导入边、轨迹邻接）中的邻近度分数。
- **阶段条件化检索策略（plan→memory）**：探索/回溯阶段用大预算、高多样性；实现阶段用小预算、高图权重，聚焦编辑点。

### 2.4 分布内注入通道（In-Distribution Injection）
- 不同于重写历史消息的做法，PMCoder **保留历史不变**，仅在最近的 tool-result 消息末尾追加 marker 分隔块（计划状态头 + 检索节点），避免破坏 tool_call↔tool_result 配对导致 out-of-distribution。
- 两个过滤器控制增长：仅计划状态变化时触发注入；已出现的节点通过 novelty filter 被一行摘要替换。

### 2.5 执行接地（Execution Grounding）
- 对每个有已验证复现脚本的实例，在文件修改编辑后重跑脚本；verdict 为 pass（问题不再复现）或 fail（仍复现）。
- 验证阶段完成谓词被硬化：零返回码仅在最新 verdict 非 fail 时才作为完成证据；终态 VERIFICATION 子任务在问题仍复现时不能完成。
- 编辑完整性：Python 文件编辑后编译检查，发现不可解析状态即追加纠正提示；失败时恢复干净基线再修复（遵循 delta-debugging 原则）。
- 所有信号均为**建议性**，不阻止动作、不直接回滚，也不参与官方 SWE-bench 评分。

### 2.6 四个跨组件耦合
1. 阶段→检索：预算、多样性权重、图权重；
2. 子任务→检索：活动子任务关键词进入检索锚点；
3. 记忆统计→计划：编辑计数、读饱和、重复动作驱动卡住检测；
4. 判定→计划：issue-reproduction verdict 更新验证阶段状态。

## 6. 主要结论与发现

- **RQ1（有效性）**：PMCoder 平均解决 167.3/500（33.5%），基线 142.3/500（28.5%），**+25.0 个案例（+5.0pp）**，95% CI [+14.3, +35.7]，p<0.001；弱运行（164）仍超过强基线（144）。难度分层显示增益集中在基础模型可解的短时层（<15min 层 +6.2pp，15min–1h 层 +6.5pp），>1h 困难尾部两者几乎都解不出——说明 PMCoder 解决的是**状态管理失败**而非基础能力上限。
- **RQ2（机制）**：失败动作重复率降至 0.50×、空补丁退出 0.33×、上下文耗尽 0.45×；revert-then-refix 恢复 1.46×。复现判定具有预测效度（解决轨迹中 90% pass，未解决中仅 28% pass）；armed 实例 +10.3pp，**unarmed（无复现脚本）仍 +3.8pp**，证明计划-记忆基座本身有效。django-13516 案例直观展示基线漂移到错误文件而 PMCoder 恢复诊断并正确定

位修复目标文件并完成验证。整体来看，PMCoder 的增益并非来自更强的单步推理（该类任务基线同样难以胜任），而是来自对轨迹状态的管理——更少重复、更少早退、更可靠地回到正轨。

- **RQ3（泛化）**：
  - 跨模型：DeepSeek-V4-Flash 上 PMCoder 相对增益与头条配置方向一致（绝对增益略低）；Claude Haiku 4.5 上同样保持正向但不显著（单次运行，样本量小，作者标注为支持性证据而非确定性结论）。增益方向跨三个不同系列模型一致，说明机制本身不依赖特定模型。
  - 框架移植：OpenHands 端口上 PMCoder 仍带来正向增益，且未破坏宿主框架的原有接口语义，表明本方法可作为插件式组件而非深度耦合的定制系统。
  - 跨基准：TerminalWorld 20 任务样本上，PMCoder 在不依赖 issue 复现脚本的场景下仍优于基线（规划-记忆耦合而非复现判定带来的增益），但提升幅度小于 SWE-bench 场景，说明执行接地的复现判定是增益的重要放大器而非唯一来源。

- **RQ4（组件消融，2×2 析因）**：plan-only 与 memory-only 各自带来正增益（plan-only 略高于 memory-only），但二者同时启用时的增益**显著大于二者之和**，交互项为正且统计显著——这是“双向耦合”优于“单向或孤立组件”的直接证据。单独验证显示：plan→memory 方向（阶段条件化检索）与 memory→plan 方向（卡住检测重规划）均各自贡献增益，移除任一方向后性能回落，但回落幅度小于同时移除（即完全退化为基线）时的损失，进一步支持双向耦合的必要性。

- **错误模式分布**（轨迹级失败分析）：
  - 基线失败中占比最高的三类为：上下文耗尽/截断后继续无效动作、重复编辑同一文件同一函数但从未运行验证、无复现脚本时在验证阶段输出“成功但补丁为空”。
  - PMCoder 剩余失败中占比最高的三类：复现判定为 pass 但官方 fail-to-pass 未全通过（判定对部分语义变化的覆盖不完全，尤其是测试涉及非执行依赖的静态属性时）；超长任务中阶段计数被“读-改-测”的合法小循环持续消耗步数但整体进展缓慢；回溯触发后恢复子任务重放旧证据导致的新方向探索不足——论文将后两者归因于步数预算守恒策略过于保守，未充分探索策略性回退的收益。

## 7. 局限性与潜在偏差

- **复现脚本的模型同源性**：复现脚本由同款 Qwen 模型离线生成，对 PMCoder 而言判定信号与生成脚本的信噪比强相关；不同源模型生成的脚本可能带来不同强度的接地效果，论文未做脚本源敏感性的系统评估。
- **单源基准偏差**：SWE-bench 全为 Python 开源仓库、问题形态为 issue 文本；未验证在私有代码库、非 Python 生态、多语言混合仓库中的行为。TerminalWorld 虽是额外锚点，但与 SWE-bench 一样属于命令行工具型任务，覆盖面上仍是同族场景。
- **统计功效受限**：多数组间配对的实例级 bootstrap 检验功效充分（500 实例 × 3 次运行），但 RQ3 各扩展实验均为单次运行，无法给出置信区间，论文也明确未将泛化数据作为主结论支撑。
- **FM（前端内存）与执行环境的耦合**：记忆节点中的编辑元数据依赖**实际执行命令**解析，对以交互式 REPL、文件内编辑（如 Jupyter 式内核回执）为主要操作方式的环境，该信号提取通道的可用性会退化；论文未覆盖此类交互范式。
- **未披露的算力细节**：无 GPU 卡型与数量、总 token 消耗、平均墙钟时间等；从描述推断的推理开销（token 预算 65k、250 步、3 次重复主实验）属于中等规模，但无法精确复现成本。
- **成功判定的二元性**：SWE-bench 以测试通过率为唯一成功标准，PMCoder 的“复现判定为 pass 但官方测试未通过”类失败提示两种判定粒度存在系统性差异（官方测试包含回归项 pass-to-pass，复现脚本只覆盖 reproduce 路径），这既是为忠实 harness 的妥协，也是对判定深度不足的坦诚。

## 8. 未来工作方向

- **学习的阶段转换与子任务分解**：当前分层规划器为确定性状态机 + 零成本规则检测器，替换为可学习的阶段分类器或 LLM 自评价阶段转移判别器，可缓解规则漏判场景。
- **记忆的跨 episode 持久化**：当前情景记忆仅覆盖单次轨迹内部；将多实例的修复模式沉淀为程序性记忆（如“此仓库的测试失败通常来自 fixture 而非业务代码”）有望提高冷启动效率。
- **判定信号的表现力扩展**：从二元复现判定扩展到多信号验证（编译错误类别、运行时 traceback 类型、测试覆盖差异），使计划状态的推进依据更丰富的执行证据。
- **预算感知的策略性回退**：在回溯触发后采用更主动的探索策略（而非仅 revert-then-refix），在耗尽步数前预留至少 10% 预算用于未知路径试探。
- **跨框架的标准嵌入协议**：将计划状态头与记忆注入块封装为环境无关的协议消息，使 OpenHands、SWE-agent、LangGraph 等宿主框架可以零侵入接入。

## 9. 总体评价

- **机制层面的贡献**：论文的价值不在于性能排行榜名次，而在于把“规划”和“记忆”从两个孤立的黑盒组件重构为一个被执行证据锚定的双向耦合状态系统。其四个跨组件耦合在机制上有清晰的可验证性——各个耦合方向均对应可量化的轨迹行为变化。
- **实验真诚度**：面对 FP8 不可位级复现的现实，作者选择多次运行 + 实例级 bootstrap 检验而非默认一次运行报告点估计；对 unarmed 实例的拆分、对复现脚本同源偏差的自陈、以及对“判定 pass 但官方未通过”的失败归类，都体现了超出通常排行榜研究的诚实度。
- **成本与高效的平衡**：在所有额外组件均为零训练、零额外监督标签、单次 LLM 调用分解子任务、记忆检索为纯词法+图计算的前提下，取得 +5.0pp 的提升，工程性价比高，具备在现有仓库级 agent 上即插即用的潜力。
- **主要保留点**：由于最优配置与模型固定在单一声源（Qwen 系）、基准集中为 Python、泛化验证单次运行，论文结论的适用范围应谨慎表述为“在 SWE-bench 类 Python 任务、开源模型成本受限场景下的机制验证”，而非普适性主张。
