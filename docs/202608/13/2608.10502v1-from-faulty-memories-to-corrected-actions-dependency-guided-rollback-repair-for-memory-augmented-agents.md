## 摘要
持久记忆使语言模型代理能够在多次会话中复用信息，但也使错误变得持久：一条有毒的、过时的或归属错误的记录可能会改变推理、工具使用、答案及后续的记忆写入。现有防御措施主要检测或删除可疑记忆，或修正当前响应。删除源头会让已经传播的声明、动作和派生记忆仍然生效，而重置存储或重放完整轨迹则会破坏良性状态并重复不必要的计算。因此，我们提出了故障后记忆恢复：给定一次失败执行和诊断出的错误记忆，在保留未受影响工作的同时恢复答案和持久状态。我们的依赖引导回滚修复从运行时溯源构建类型化的记忆-动作图，追踪显式的下游依赖，保留具有独立可信支持的候选，停用不支持的记忆状态，并仅选择性地重放与答案相关的受影响计算。我们在一个包含三个工具使用领域和四种记忆故障类型的150例受控基准上，以及在从LongMemEval-V2改编的50例轨迹衍生压力测试上评估了该方法。在受控基准上，它实现了85.3%的恢复率，而最佳竞争恢复方法为77.3%，它移除了所有诊断出的错误记忆，保留了所有良性记忆，并且仅需选择性的重放，LLM调用成本适中。在改编子集上，它达到了68.0%的恢复率，而次优方法为54.0%，同时实现了最高的声明失效F1，为0.669对比0.603。总体而言，这些结果并不意味着轨迹重建在所有方面都更好，但表明依赖引导回滚修复在修复错误记忆状态并保留良性记忆的同时，提供了强大的恢复-成本权衡。

## Abstract
Persistent memory lets language-model agents reuse information across sessions, but it also makes errors durable: a poisoned, stale, or misattributed record can alter reasoning, tool use, answers, and subsequent memory writes. Existing defenses mainly detect or delete suspicious memories, or revise the current response. Deleting the source leaves already propagated claims, actions, and derived memories active, whereas resetting the store or replaying the full trace destroys benign state and repeats unnecessary computation. We therefore formulate \textbf{post-failure memory recovery: } \textit{given a failed execution and diagnosed faulty memories, recover both the answer and persistent state while retaining unaffected work.} Our \textbf{dependency-guided rollback repair} builds a typed memory-to-action graph from runtime provenance, traces explicit downstream dependencies, preserves candidates with independent trusted support, deactivates unsupported memory state, and selectively replays only answer-relevant affected computation. We evaluate this approach on a 150-case controlled benchmark spanning three tool-use domains and four memory failure types, and on a 50-case trajectory-derived stress test adapted from LongMemEval-V2. On the controlled benchmark, it achieves 85.3\% recovery versus 77.3\% for the best competing recovery method, removes all diagnosed faulty memories, preserves all benign memories, and requires only selective replay with modest LLM-call cost. On the adapted subset, it reaches 68.0\% recovery versus 54.0\% for the next best method, while also achieving the highest claim invalidation F1, 0.669 versus 0.603. Overall, the results do not imply uniformly better trace reconstruction, but show that dependency-guided rollback repair provides a strong recovery--cost trade-off while repairing faulty memory state and preserving benign memory.

### 1. 核心问题与整体含义

**研究背景：**
- 记忆增强代理（Memory-Augmented Agents）通过持久记忆在多次会话中复用用户的偏好、观察和经验，实现个性化和长期行为支持。
- 持久记忆在带来便利的同时，也使得错误变得**持久化**：一条有毒（poisoned）、过期（stale）、张冠李戴（misattributed）或漂移（drifted）的记忆记录，一旦被检索为上下文，就可能导致错误的推理、工具调用计划、最终答案，甚至被固化（consolidate）为新的错误记忆，形成错误的"传播链"。

**核心问题——"故障移除 ≠ 状态恢复"：**
- 现有防御手段存在明显缺口：
  - **仅删除源头记忆** → 已传播的声明（claims）、动作（actions）和派生记忆（derived memories）仍然保持激活状态，会继续影响未来轮次；
  - **仅修正当前响应** → 错误源头与受污染的衍生状态依然存在；
  - **重置整个记忆库** 或 **重放完整轨迹** → 破坏良性状态，造成大量不必要的计算。
- 因此论文正式提出**故障后记忆恢复（post-failure memory recovery）**问题：给定一次失败的执行和已诊断出的错误记忆，既要恢复最终答案和持久记忆状态，又要保留未受影响的工作。具体而言，需要回答三个子问题：哪些后果应被撤销（invalidate）、哪些仍具有独立依据（independently justified）、哪些必须重新生成（regenerate）。

**整体含义：**
- 本文将"记忆错误恢复"从单一的记忆删除或回答修正，扩展为**联合修复持久记忆库 + 异构执行轨迹（claims/plans/tool actions/observations/answers）**的整体性问题，并提出了首个面向端到端恢复的解决方案。

### 2. 方法论：依赖引导的回滚修复（Dependency-Guided Rollback Repair）

**核心思想：**
- 利用运行时溯源（runtime provenance）构建**类型化记忆-动作依赖图**（typed memory-to-action graph），从已诊断的错误记忆出发，显式追踪下游数据依赖；
- 通过**独立支持检查（independent-support checking）**避免过度失效，保留有独立可信依据的状态；
- 通过**确定性规则引导的回滚规划器**删除错误记忆、隔离（quarantine）不支持的派生记忆、失效（invalidate）不支持的轨迹输出，并筛出**与答案相关**的受影响计算；
- 最后**选择性重放（selective replay）**被选中的步骤，复用安全上下文，在修复后的记忆状态下按轨迹顺序重新执行，生成修正后的最终答案。

**五个阶段的技术流程（对应 Figure 2）：**

1. **依赖图构建（Dependency Graph Construction）**
   - 构建有向异构图 G = (V, E)，节点分为用户输入（V_U）、执行步骤（V_T，含类型）和持久记忆记录（V_M）；
   - 边通过确定性规则从运行时字段实例化，而非 LLM 推断，类型包括：initiate（发起）、cite（引用）、support（支持）、produce（产生）、delete/update/consolidate（记忆生命周期操作）、supersede（取代）、derive（派生）、chain（时序链）；
   - 传播使用 E_prop（排除纯 chain 边）——**"时间上在后"不等于"被污染"**，这一区分避免误伤顺序后缀中的无关有效工作。

2. **故障溯源与受影响子图追踪（Fault Provenance & Affected Subgraph Tracing）**
   - 对每个错误记忆 m∈F，通过 delete/update/consolidate 关系回溯到"变异种子"（mutation seed）r(m)；
   - 从种子出发沿 E_prop 进行前向可达性传播，取并集得到原始受影响候选集 A₀ = ∪_{m∈F} Reach(V, E_prop)(r(m))；
   - 该集合**有意过估计（over-approximate）**，偏向召回，留待下一步精化。

3. **独立支持检查（Independent-Support Checking）**
   - 对 A₀ 中每个可语义检查的候选节点 v，收集其充分证据前驱 Pred_sup(v)（通过 support/derive/supersede 及充分 cite 关系）；
   - 固定信任策略（fixed trust policy）认定可信来源包括：显式当前轮指令、未被诊断为错误的激活记忆、成功的工具观察、未受影响的已验证声明；
   - 判定条件：TrustedSupport(v) ⇔ ∃ p ∈ Pred_sup(v)，满足 p ∉ F ∪ A₀ 且 Admissible(p)；
   - **保守性设计**：已保存的候选不能递归地用于验证其他候选，防止相互依赖的错误节点形成"互证"；最终得到不支持集 A = A₀ \ P_sup。

4. **规则引导的回滚规划（Rule-Guided Rollback Planning）**
   - 确定性规划器，非优化式；核心决策：
     - **删除**（Delete）：诊断出的错误记忆 M_del = F；
     - **隔离**（Quarantine）：不支持的受影响记忆 M_quar = (A ∩ V_M) \ F，保留在审计分区但不再参与检索与执行；
     - **失效**（Invalidate）：所有不支持的轨迹节点 V_inv = A ∩ V_step，其输出不得再作为证据；
     - **保留**（Preserve）：有独立支持的节点及其安全动作/观察节点，作为固定上下文复用；
     - **重放**（Replay）：仅重放与答案相关的受影响执行节点。
   - **答案相关性判定**：在删除/隔离记忆后的图 G⁻ 中，定义 A_ans = {v ∈ A ∩ V_step | v ⇝ v_final in G⁻}，即只有修复后的输出仍可能贡献于最终答案的节点才需重放；
   - **可执行重放集**：V_replay = ExecClosure(A_ans ∪ {v_final})，递归补充被失效的执行前驱（受影响的记忆读取、控制计划、工具动作、生产者步骤、记忆变异步骤）；工具观察不直接重放，而是通过调度其生成动作来刷新；
   - 最终答案节点恒被重放。

5. **选择性重放（Selective Replay）**
   - 先应用记忆处置，得到修复前活动记忆 M⁻ = M \ (M_del ∪ M_quar)；
   - 按原始轨迹顺序处理 V_replay，V_preserve 作为固定上下文提供，失效但不在重放集中的节点永久排除；
   - 被失效的声明在生成替代品之前不得被后续步骤引用；重放的记忆读取只从修复后的存储检索；记忆变异仅在修复执行证据支持下才被应用；
   - 对于带副作用的工具，只有在存在可重置/幂等/补偿接口的假设下才重新执行；
   - 最终输出：修正答案 y'_final、修复后轨迹 T'、修复后记忆库 M'。

**对比方法（6个基线）：**
1. **No repair**（下界）：保持故障状态不变；
2. **Full memory reset**（记忆重置）：删除全部激活记忆后重放最终轮；
3. **Delete retrieved memories**（删除检索到的记忆）：删除受故障影响区域中出现的激活记忆后重放最终轮；
4. **MemAudit-style**（后验记忆审计，Tan et al. 2026）：对候选记忆做一致性异常评分 + 反事实影响评分（α=0.5 加权），超过 0.5 阈值即删除；空候选池时回退到 oracle 辅助诊断（非无监督）；
5. **LLM-judge repair**（受 Reflexion/Self-Refine 启发）：让 LLM 从紧凑故障信息中预测回滚计划，计划须经校验并删除所有诊断故障记忆，再由同一回放执行器执行；

**充分性与公平性评估：**
- **优点**：覆盖多个领域、多种故障类型、多个基线和多个骨干模型；消融设计清晰，准确归因各组件贡献；迁移实验验证了外部数据集适用性；所有方法共享同一执行器和评估流程，公平性较好；
- **不足**：单次运行（temperature=0, seed=42），无多次重复实验的标准差报告；缺少跨 seed 的统计显著性检验；受控基准规模中等（150例），Adapted LongMemEval-V2 子集非完整基准分布，不能代表整体性能。

### 6. 主要结论与发现

1. **受控基准上达到最高恢复率**：85.3%（vs LLM-judge repair 77.3%、AgentTrace-style 60.7%）；绝对提升 8.0 和 24.6 个百分点；是 Full memory reset 的 2 倍以上、Delete retrieved memories 和 MemAudit-style 的约 2.5 倍；
2. **完美实现故障清除与良性保留**：删除所有诊断出的错误记忆（100%），保留 100% 良性记忆（LLM-judge repair 同为 100% 保留，但重放和 LLM 调用成本更高）；
3. **恢复-成本权衡出色**：相比 LLM-judge repair，重放比例降低 43.3%，LLM 调用降低 41.8%；相比 AgentTrace-style，恢复率大幅提升（+24.6pp），代价是更多的重放和 LLM 调用；
4. **复发率非最优**：26.6%，高于 LLM-judge repair（12.1%），但低于 AgentTrace-style（34.1%）和 Delete retrieved memories（43.1%）；需与恢复率联合解读，不能孤立看待；
5. **声明失效 F1 并非最高**：0.566（受控基准），低于 LLM-judge repair（0.946）和 AgentTrace-style（0.853），但这并未转化为更好的端到端修复效果；
6. **迁移集上全面领先**：恢复率 68.0%（vs AgentTrace-style 54.0%）；声明失效 F1 最高（0.669 vs 0.603）；绝对恢复率从 85.3% 降至 68.0%，说明受控基准结果是上界而非部署估计；
7. **消融结论明确**：回滚规划器对恢复和复发贡献最大；支持检查以轻微恢复率下降换取更高的选择性和良性保留；选择性重放大幅降低修复成本（重放比例降 83.7%、LLM 调用降 76.3%），但以复发率上升为代价（26.6%→7.1% 为反向）；
8. **分域/分类型差异显著**：购物最难（72.9%），客户支持最高（94.3%）；wrong-user 最难恢复（70.6%），summary-drift 最高（95.0%）；stale 故障复发率很高（78.1%）但恢复率也很高（94.1%）——答案修复成功而状态抑制脆弱；
9. **骨干迁移性稳健**：三种 LLM 下方法表现一致，虽绝对恢复率随骨干减弱而下降。

### 7. 优点

**方法设计上的亮点：**
1. **问题定义新颖且准确**：明确提出"故障移除 ≠ 状态恢复"，将恢复目标从单点修正扩展为"答案 + 持久状态 + 良性保留 + 成本"四重联合优化；
2. **依赖图设计精细**：类型化节点和边（10种关系标签），明确区分传播边（E_prop）与时序链边（chain），既避免漏追踪也避免时序误伤；
3. **独立支持检查机制巧妙**：防止"可达即失效"的过激做法，引入保守的固定信任策略，且禁止已保存节点递归互证，逻辑严谨；
4. **答案相关性筛选有效**：通过 G⁻ 中可达性来定义 A_ans，使无效化与重放解耦——"失效但不必重放"和"重放但保留支持"两个维度正交处理，设计精妙；
5. **成本意识强**：选择性重放和保留（preserve）机制使成本可控，与 LLM-judge repair 相比恢复更高、成本更低；
6. **规则的确定性与可复现性**：规划器完全确定性（rule-guided 而非 optimization-based），图构建和边实例化不依赖 LLM 推断，实验可复现性强；
7. **假设边界交代清晰**：外部副作用不可逆问题、需要可重置/幂等/补偿接口等前提都在问题设定中说明。

**实验设计上的亮点：**
1. 同时构建受控基准和外部迁移基准，兼顾内部有效性和外部泛化性；
2. 消融实验指向性强，能准确定位每个组件的贡献与代价；
3. 成本评估维度全面（重放比例、LLM 调用数、总 token 数）；
4. 案例研究覆盖单故障、多故障、工具调用重放、根记忆错误等场景，直观展示工作机理。

### 8. 不足与局限

**实验覆盖层面的局限：**
1. **复发率非最优**：受控基准上复发率为 26.6%，高于 LLM-judge repair 的 12.1%；论文虽从"条件于恢复集"的角度解释了低恢复率方法的假优势，但 26.6% 的复发率仍说明修复后的记忆状态在后续使用中不够稳健；
2. **声明失效 F1 显著低于两个轨迹中心基线**（0.566 vs 0.946/0.853），
