## 摘要
我们提出了ARBIGRAPH，一个用于评估工具辅助语言代理是否能在扩展推理工作流中保留、更新、组合和丢弃任务相关上下文的基准生成器。ARBIGRAPH将每个任务表示为一个自然语言问题，并附带可执行的Python求解器，通过类型化的中间状态（此处实例化为标量和列表值）组合任务。这种设计支持可控的任务图，其长度、依赖结构、干扰项数量和值类型可以变化，同时保持精确的自动验证。我们使用数学、GSM风格的文字问题和Python追踪任务类别实例化ARBIGRAPH，并在四种拓扑结构上评估了Qwen3.5-27B工具辅助代理。结果显示，在孤立任务上准确率很高，但在更复杂的依赖任务上显著下降：在分支链式依赖数学任务中准确率下降高达33.3%。这表明ARBIGRAPH揭示了仅通过单任务评估无法观察到的失败。我们的代码、生成的数据集和评估结果可在https://github.com/pavelgolikov/ArbiGraph.git获取。

## Abstract
We introduce ARBIGRAPH, a benchmark generator for evaluating whether tool-assisted language agents can retain, update, compose, and discard task-relevant context across extended reasoning workflows. ARBIGRAPH represents each task as a natural-language problem with an executable Python solver, and composes tasks through typed intermediate states, instantiated here as scalar and list values. This design enables controllable task graphs whose length, dependency structure, distractor count, and value type can be varied while preserving exact automatic verification. We instantiate ARBIGRAPH with math, GSM-style word-problems, and Python-tracing task categories, and evaluate a Qwen3.5-27B tool-assisted agent across four topologies. The results show high accuracy on isolated tasks but substantial degradation on more complex dependent tasks: accuracy drops by up to 33.3% on branching chains of dependent math tasks. This shows that ARBIGRAPH exposes failures that are not visible from single-task evaluation alone. Our code, generated datasets, and evaluation results are available at https://github.com/pavelgolikov/ArbiGraph.git

## 1. 核心问题与整体含义（研究动机和背景）

- **研究动机**：语言模型代理（agent）在执行长工作流时，不仅需要局部问题求解能力，更关键的是**上下文管理**能力——保留有用信息、更新中间状态、丢弃无关或过时信息。现有基准多聚焦于单任务推理、长文档检索或固定组合模式（如打包独立问题、指令序列），未能将**依赖拓扑本身**作为可控变量来测试代理的状态传播、选择性遗忘和跨任务干扰。
- **背景问题**：高基线准确率并不保证复杂依赖场景下的表现；现有评估无法区分“局部任务失败”与“上下文管理失败”。
- **核心贡献**：ArbiGraph 将上下文视为**类型化的计算状态**，通过可定制的依赖图自动生成可验证的评估实例，从而暴露仅单任务评估无法发现的缺陷。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：将每个任务建模为带可执行 Python 求解器的自然语言问题，通过**类型化中间状态**（标量、列表）组合为有向无环图（DAG）。用户指定拓扑（节点数、依赖结构、干扰数、值类型），生成器自动渲染为单个提示（prompt），并保留所有中间和最终 ground truth 用于自动验证。
- **关键技术细节**：
  - **任务节点**：元组 `(输入, 前适配器, 提示, 后适配器, 输出, 求解器)`。适配器用于类型转换（如取模、截断、舍入），保持局部任务语义与全局可组合性分离。
  - **任务组合**：通过命名输出变量绑定依赖关系，输出类型必须匹配输入类型（标量/列表）。
  - **拓扑类型**：
    - **Baseline**：仅目标任务（单节点）
    - **Forgetting**：目标前插入 3 个独立干扰任务
    - **Chain**：线性依赖链（4 节点）
    - **Multi-Chain**：分支汇聚图（8 节点，列表输出→多个标量分支→重新组合为列表→最终任务）
  - **任务类别**：
    - **Math**：40 个手工选择运算符（线性代数、多项式、数论等）覆盖所有类型签名（scalar→scalar, list→scalar, 等）
    - **Python Tracing**：80 个 LeetCode 算法（追踪执行）
    - **GSM-Symbolic**：41 个带自然语言变异的文字算术题
  - **适配器**：对中间值进行取模（≤100）、截断列表长度（≤10）、类型强制等，防止输出爆炸或退化。

## 3. 实验设计：数据集、基准、对比方法

- **数据集/场景**：每个任务类别生成固定数量样本：每任务 16 个样本（随机种子 0），过滤退化输出（如 0、1、-1、空列表、重复列表等）。整体生成规模：Math 40 任务 × 16 = 640 个实例/拓扑；Python 80 × 16 = 1280；GSM 41 × 16 = 656（不含多链，因为 GSM 仅输出标量无法分支）。
- **基准**：以**最终任务准确率**为主要指标，辅以**平均 token 数**和**平均交互轮次**。
- **对比方法**：**未对比其他 agent 或模型**。仅对比同型号（Qwen3.5-27B）在不同拓扑上的表现。本质是拓扑消融（baseline vs forgetting vs chain vs multichain），而非模型间对比。

## 6. 主要结论与发现

- **基线高，复杂拓扑显著退化**：
  - 数学：baseline 94.5% → forgetting 89.2% → chain 75.5% → multichain 61.2%（下降 33.3 个百分点）
  - Python Tracing：baseline 96.8% → forgetting 92.5% → chain 90.1% → multichain 90.5%（相对稳定）
  - GSM：baseline 100.0% → forgetting 100.0% → chain 96.0% → multichain 不可用
- **不同任务类别对上下文管理敏感度不同**：数学最敏感，Python 追踪较鲁棒。这反映出类型化状态传播依赖于领域语义。
- **过程指标印证困难增加**：在困难拓扑中，平均 token 数和交互轮次显著上升（数学 chain/multichain 的 token 从 10K 增至 52K，轮次从 7 增至 13），说明代理确实付出了更多推理努力。

## 7. 优点

- **方法论创新**：将上下文管理形式化为“类型化状态传播”，与单任务推理脱钩，依赖拓扑本身作为实验变量。这弥补了现有基准（如 Lost in the Middle、LongBench）只关注检索或位置偏差的不足。
- **自动生成与验证**：完全自动化，可任意扩展图大小和复杂度，支持用户自定义 DAG，易于复现。
- **多样化任务类别**：涵盖数学、代码追踪、文字算术，覆盖不同推理风格，增加评估全面性。
- **过程指标**：不仅报告准确率，还记录 token、轮次等过程度量，帮助区分失败原因（是 reasoning failure 还是 context management failure）。
- **开源**：代码、数据、结果公开，促进社区后续研究。

## 8. 不足与局限

- **模型覆盖狭窄**：仅评估 Qwen3.5-27B，未与 GPT-4、Llama-3、Claude 等主流模型对比，结论的泛化性有限。
- **类型系统有限**：仅支持标量和列表，不支持更丰富的类型（如图像、JSON、数据库行），尚未扩展到多模态。
- **拓扑结构简单**：仅测试了固定大小的 4 种拓扑（最多 8 节点），未探索更深、更宽、更复杂的图（如循环、条件分支），也未模拟实际工作流（如工具调用、外部 API）。
- **修复协议可能引入偏倚**：允许大量修复轮次（多链最多 24 次），可能高估代理的真实能力，且不同拓扑修复预算不同，对比不够严格。
- **GSM 类别不完整**：无法构造多链，导致该维度缺失。
- **计算资源未充分利用**：仅报告总推理时间，未明确并行度，无法评估运行成本。
- **缺乏对 agent 内部机制的诊断**：虽然能检测到性能下降，但无法精确定位失败是由于“忘记传递值”还是“计算错误”还是“干扰导致注意力偏移”。
