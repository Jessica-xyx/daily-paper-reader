## 摘要
大语言模型代理日益依赖长期记忆来支持多会话交互和个性化。然而，现有的代理记忆系统围绕仅前向演化设计，不断累积、整合和覆盖知识，缺乏检查、版本化或回退先前状态的原则性机制。这使得代理在修正、概念漂移和记忆损坏面前变得脆弱，尤其是在它们已经接触后续信息之后。我们提出了ChronoMem，一个面向代理记忆的语义版本控制层，集成到Google的生产级开源Agent Development Kit中。ChronoMem在每次内存写入时提交整个内存快照，维护结构化的版本历史，并通过混合词汇和语义检索、排名融合和重排序，将撤销意图映射到具体的历史版本，从而支持自然语言的回滚请求。我们进一步引入了一种暴露后评估协议，通过回答查询和总结历史来测试代理在回滚后是否能以反事实的方式表现，就好像未来更新从未发生过一样。在增加了演化记忆状态和回滚任务的长周期对话基准上，相对于仅提示和仅检索的基线，ChronoMem在回滚一致的问答和历史总结方面显著提升，同时在语义版本选择方面表现出强劲性能。据我们所知，ChronoMem是第一个用于LLM代理中系统性语义全局记忆回滚的开源系统和基准。

## Abstract
LLM agents increasingly rely on long-term memory to support multi-session interaction and personalization. However, existing agent memory systems are designed around forward-only evolution, continuously accumulating, consolidating, and overwriting knowledge, with no principled mechanism to inspect, version, or revert prior states. This makes agents brittle under corrections, concept drift, and memory corruption, particularly after they have already been exposed to subsequent information. We present ChronoMem, a semantic version-control layer for agentic memory integrated into the production-ready, open-source Agent Development Kit by Google. ChronoMem commits whole-memory snapshots at each memory write, maintains structured version histories, and supports natural-language rollback requests by mapping undo intents to concrete historical versions through hybrid lexical and semantic retrieval, rank fusion, and reranking. We further introduce a post-exposure evaluation protocol that tests whether an agent can behave counterfactually after rollback by answering queries and summarizing history as if future updates had never occurred. On long-horizon conversational benchmarks augmented with evolving memory states and rollback tasks, ChronoMem substantially improves rollback-consistent question answering and history summarization relative to prompt-only and retrieval-only baselines, while achieving strong performance in semantic version selection. To our knowledge, ChronoMem is the first open-source system and benchmark for systematic semantic global memory rollback in LLM agents.

  - 无法将自然语言"撤销"请求映射到正确的历史版本；

  - 面对错误累积、概念漂移、记忆投毒等场景时代理表现脆弱。
- **整体含义**：这篇论文提出将代理记忆从"被动累积"转向"主动管理、可逆、可语义搜索"的受控状态，为可回滚的长期记忆建立了首个开源系统与评估基准。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 核心思想

ChronoMem 将长期代理记忆建模为一个**版本化状态机**：每次记忆写入生成一次"提交"（commit），创建整个记忆的全局快照，形成线性版本历史。自然语言回滚请求通过"NL→版本"语义解析映射到具体版本，然后由确定性的数据平面原语恢复快照状态。

### 总体架构（四阶段流水线）

1. **阶段一：版本构建（Commit-on-Write）**——每次记忆写入操作触发新版本创建（见 Algorithm 1）：
   - 向不可变事件日志 L 追加事件 e_i；
   - 生成语义提交描述符 d_j = {delta, summary, op, labels}，涵盖操作级变更、自然语言摘要、更新类型、时间元数据；
   - 物化全记忆快照 S(v_j)，持久化版本元数据与快照负载；
   - 推进 HEAD 指针至最新版本（事务保证原子性）。

2. **阶段二：版本索引（语义提交描述符）**——对每个版本的描述符 d_j 建立二级索引：
   - 支持 SQLite FTS5 BM25 词法检索；
   - 同时生成向量嵌入支持稠密检索。
   - 关键设计：检索在版本级描述符上进行，而非全快照或原始事件，保证选择成本仅与版本数量相关，与快照大小无关。

3. **阶段三：NL→版本映射（混合检索 + 重排序）**：
   - 并行执行 BM25 词法检索与向量稠密检索（Top-K）；
   - 使用**倒数秩融合（RRF）** 合并两个排名列表：RRF(v_j|q) = Σ_m 1/(k₀ + rank_m(v_j))，k₀ 通常取 60；
   - 可选使用更强的交叉编码器（如 Cohere Rerank-3.5）对融合候选进行重排序，取 Top1 作为目标版本。

4. **阶段四：确定性回滚执行**（见 Algorithm 2）：
   - LoadSnapshot 加载目标版本的快照；
   - RestoreStateFromSnapshot 恢复本地记忆状态；
   - SetHead 更新活动版本指针；
   - TruncateVersionsAfter 截断后续版本，维持线性历史；
   - SynchronizeRetrievalBackendIfAny 同步检索索引（尽力而为、幂等）。
   - 提供两层接口：`rollback_to_version(version_id)`（ID 确定恢复）与 `rollback_to_version_by_nl_query(query)`（语义解析后委托给前者）。

### 接口不变式

回滚后的所有记忆读取严格限定在 HEAD 指向的版本范围内——即恢复到 v* 后，代理必须表现得仿佛 v* 之后的信息从未存在过（反事实行为）。

## 3. 实验设计

### 数据集与场景

| 数据集 | 用途 | 适配方式 |
|--------|------|----------|
| **LoCoMo** | 非常长的多会话对话基准，含 QA 与事件总结任务 | 用标注的 QA 证据跨度确定目标版本 v*，构造回滚查询 |
| **MemoryAgentBench (MAB)** | 增量多轮交互记忆基准，含精确检索、测试时学习、长程理解、冲突消解四类能力 | 利用构造的更新边界确定目标版本，仅在 Accurate Retrieval 子集上评估 QA |

### 评估协议：暴露后回滚（Post-Exposure Rollback）

- **阶段一（暴露）**：让代理消化完整交互流直到最终状态 v_T；
- **阶段二（回滚）**：发出自然语言回滚请求，恢复到指定版本 v*，然后执行下游任务（QA 或总结）。
- 这要求代理**反事实**地行为——已看到 v* 之后的信息但须表现得仿佛这些信息不存在。

### 对比基线

1. **Prompt-only rollback**：仅提供自然语言回滚指令，不改变底层记忆状态；
2. **Full-history prompt rollback**：将完整历史（含 v* 后内容）放入输入并指示模型"假设回滚"，最大污染压力测试；
3. **Retrieval-only rollback（RAG-only）**：通过向量 ANN 检索相关历史片段，不恢复全局版本快照。

### 评估指标

- **RQ1 版本选择**：Recall@1、Recall@5、Scope@2（时间局部性，|v̂ − v*| ≤ 2 的概率）；
- **RQ2 回滚一致问答**：F1（LoCoMo）、任务准确率（MAB）；
- **RQ3 回滚一致总结**：ROUGE-1（LoCoMo）、F1（MAB En.Sum）。

## 6. 主要结论与发现

1. **语义版本选择**：ChronoMem 在 Recall@1 上显著优于混合检索基线（LoCoMo：12.0%→20.5%；MAB：24.3%→33.4%）。重排序阶段对解决相邻语义相似版本的歧义至关重要（Scope@2 提升约 13–17 个百分点）。
2. **回滚一致 QA**：相对于最强非版本化基线（RAG-only），ChronoMem 在所有背骨模型上一致提升（LoCoMo 上约提升 7–12 个百分点 F1；MAB 上约提升 8–21 个百分点）。Prompt-only 几乎接近随机水平（≤3%），证明后暴露污染无法通过指令跟随克服。
3. **回滚一致总结**：ChronoMem 始终最优（LoCoMo ROUGE-1 提升 0.04–0.03；MAB 上显著超越 RAG-only，从约 3% 提升至 13–14%）。
4. **核心论点**：后暴露下的回滚一致行为主要是**架构性属性**——由显式版本作用域的状态恢复赋予，无法仅通过提示或片段级相似度检索可靠涌现。

## 7. 优点与亮点

- **系统完整性**：选择生产级开源框架（Google ADK）做集成，实用性强，非仅学术概念验证。
- **清晰的抽象分层**：将语义回滚拆解为"选择"（NL→版本解析，控制平面）与"恢复"（确定性快照恢复，数据平面），两者解耦使评估可解释。
- **事件溯源 + 快照双设计**：兼顾可审计性（增量事件日志可重建）与恢复效率（快照避免重放全部日志）。
- **混合检索 + 重排序管线**：版本级语义描述符索引而非全量快照搜索，计算成本与版本数而非快照大小成正比。
- **新颖的评估标准**：首次提出"暴露后回滚"协议，强制测试反事实行为，切中实际场景中"已看到后续信息但需回到历史状态"的核心需求。
- **开源贡献**：论文明确声称这是首个面向 LLM 代理语义全局记忆回滚的开源系统与基准。

## 8. 不足与局限

### 技术局限

- **并发与事务**：使用每用户锁 + SQLite 事务，SQLite 单写者特性导致高并发场景可能产生写竞争。未实验评估多会话/多用户并发下的行为、冲突与扩展性（WAL/WAL2 优化留待未来）。
- **仅线性历史**：回滚后截断后续版本（Git reset 风格），不支持分支、合并或"回滚后恢复"的复杂版本拓扑。
- **检索后端同步为尽力而为**：若索引同步失败，可能产生本地状态与检索状态不一致的窗口。

### 评估局限

- **基准适配偏差**：LoCoMo 与 MAB 并非为回滚设计，构造的回滚查询分布可能无法反映真实用户意图的多样性、模糊性和部分限定性。
- **查询生成约束**：不允许版本 ID、时间戳、会话索引出现在回滚查询中，但锚点本身由标注推导，现实中用户可能以更自然但更模糊的方式表达。
- **背骨规模限制**：仅测试 7B–8B 模型，未覆盖大规模（如 70B+）或小规模（<7B）模型。不同规模模型在指令跟随能力和抗污染能力上的差异可能影响结论。
- **数据子集覆盖不全**：MAB 上仅评估 Accurate Retrieval，未展示 Test-Time Learning 等能力上的回滚表现。
- **缺少生产级规模验证**：论文自己也承认，结果展示的是受控长时对话下的架构稳健性，而非生产级代理部署中回滚行为的完整刻画。

### 外部效应边界

- **不处理任意外部副作用**：超出代理记忆基板的外部服务状态无法被恢复，与应用相关的回复仍需应用层配合（与现有回绕机制一致）。
