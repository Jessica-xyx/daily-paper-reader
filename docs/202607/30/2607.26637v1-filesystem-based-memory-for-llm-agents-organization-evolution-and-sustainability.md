## 摘要
部署的LLM智能体越来越多地将长期记忆存储为文件系统：一个由Markdown文件组成的目录树，智能体通过通用文件工具自行读写和重组。然而，研究在很大程度上忽视了这一媒介：先前的系统设计定制了记忆表示并研究其检索，而未检验默认方案的两个工作假设：智能体能否在记忆积累、冲突和过时的情况下保持存储的有序组织，以及这种组织是否值得。我们首次对基于文件系统的LLM智能体记忆进行系统探索。我们将该设定形式化为围绕一个记忆文件系统的三个角色：管理智能体整合和组织传入内容，搜索智能体用引用的来源回答查询，执行智能体提供任务轨迹并蒸馏为技能，将陈述性记忆和技能统一在单一存储中。在长对话基准和具身任务中，我们改变记忆形态（智能体组织的层次结构、逐字转储、分块检索）、流规模、工具集（沙盒shell、记忆工具式函数、多种搜索工具）以及管理和搜索智能体的能力，追踪记忆增长时的答案质量、成本和存储健康。组织所带来的可靠收益是搜索经济性：当材料规模大时，有组织的存储大致使检索成本减半。然而，当今的智能体未能达到默认方案的承诺：在我们的增长研究中，除了最强的管理智能体，其他智能体的组织性都会下降，并且我们测量的任何智能体都无法将组织本身转化为更好的答案。而且，模型并非影响存储形态的唯一杠杆：仅改变工具集就能像更换模型一样强烈地改变存储形态。这项研究将文件系统默认从一种假设转变为智能体记忆的设计空间。

## Abstract
Deployed LLM agents increasingly keep their long-term memory as a filesystem: a directory tree of markdown files that the agent itself reads, writes, and reorganizes through generic file tools. Yet research has largely passed over this medium: prior systems design bespoke memory representations and study retrieval over them, leaving the default's two working assumptions untested: that an agent can keep a growing store organized as memories accumulate, conflict, and go stale, and that this organization pays. We present the first systematic exploration of filesystem-based memory for LLM agents. We formalize the setting as three roles around one memory filesystem: a management agent integrates and organizes incoming content, a search agent answers queries with cited sources, and an execution agent supplies task trajectories that are distilled into skills, unifying declarative memory and skills in a single store. Across long-conversation benchmarks and embodied tasks, we vary memory shape (agent-organized hierarchy, verbatim dump, chunk retrieval), stream scale, tool harness (sandboxed shell, memory-tool-style functions, varied search tooling), and the strengths of the management and search agents, tracking answer quality, cost, and store health as memory grows. What organization reliably buys is search economy: organized stores roughly halve retrieval cost where material is large. Today's agents, however, fall short of the default's promise: in our growth study, organization erodes for all but the strongest management agent, and no agent we measure converts organization itself into better answers. And the model is not the only lever over a store's shape: changing the tool set alone reshapes the store as strongly as swapping the model. The study turns the filesystem default from an assumption into a design space for agent memory.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究动机**：当前部署的LLM智能体（如编码助手、长期对话助手）越来越多地将长期记忆存储为一个**文件系统**——即由智能体自己读写和重组的Markdown文件目录树。业界默认了这一做法（例如Anthropic的Memory Tool、Claude Code、OpenAI的Dreaming），但学术界却很少系统研究这种媒介本身的有效性。
- **核心问题**：智能体能否在记忆不断积累、冲突、过时的情况下，保持文件系统存储的**有序组织**？这种组织是否值得付出额外成本？即文件系统默认假设的两个核心前提是否成立。
- **整体含义**：如果组织不能带来收益，或者智能体无法维持组织，那么当前部署实践就失去了理论支撑。本文首次系统探索这一问题，旨在将文件系统记忆从“默认假设”转变为可设计、可优化的**设计空间**。

## 2. 论文提出的方法论

### 核心思想
- 将基于文件系统的智能体记忆形式化为三个角色围绕一个共享文件系统进行协作：
  - **管理智能体（Management Agent）**：负责将每个新来的内容块整合到存储中，同时保持存储的组织性（包括创建、合并、拆分、移动、重命名、删除文件或文件夹）。
  - **搜索智能体（Search Agent）**：在固定存储上回答查询，返回带有文件路径引用的答案（只读操作）。
  - **执行智能体（Execution Agent）**：在技能（procedural memory）场景中出现，接收检索到的技能文件并执行任务，其成功与否作为存储质量的探针。
- **统一存储**：陈述性记忆（事实、事件、偏好）和过程性记忆（技能）都存储在同一个文件系统中，文件结构相同（YAML frontmatter + Markdown正文），通过`metadata.type`区分。
- **工具集（Tool Harness）**：智能体通过可互换的工具集访问存储，包括：
  - 默认文件工具（view, create, str_replace, insert, delete, rename, grep）
  - 增加BM25全文搜索的变体
  - 全功能Shell（bash, grep, sed, awk等）
- **管理智能体的核心指令**：遵循五个组织原则（P1–P5：子节点可区分、子节点相关、父节点覆盖子节点、距离反映相关性、结构服务于搜索），并包含因果推理、时间锚定、源归因等约束。

### 关键技术细节
- 每个文件以YAML frontmatter开头（name, description, 可选metadata），描述是搜索的关键表面。
- 管理智能体在每个块到来时执行“调查→捕获→归档→维护”四步流程，包括跨文件检查、引用维护、时间一致性处理。
- 搜索智能体执行“调查→路由→只读需要的内容→验证后停止”策略，成本模型强调每次工具调用都会重新发送整个对话历史。
- 在技能场景中，管理智能体将执行轨迹蒸馏为可重用的技能或记忆笔记，且有严格的输出门（仅成功尝试可创建或扩展正向技能，失败尝试只能产生避免陷阱的笔记）。

## 3. 实验设计

### 数据集与场景
- **对话记忆场景**（陈述性记忆）：
  - **LoCoMo**：多会话长对话，158个问题（排除对抗类别），涵盖多跳、时序推理、开放域、单跳。
  - **PersonaMem**：32k和128k两个token层级的个性化记忆多选问答，共3条对话（32k）和1条对话（128k）。
  - **REALTALK**：21天真实人际对话，85个问题。
- **过程记忆场景（技能）**：
  - **ALFWorld**：具身家庭任务，共140个任务，跨越6个目标族（放置、双物体、检查、清洁、加热、冷却）。
  - 两种评估协议：三链协议（独立三条链，存储重置）和全链协议（140个任务一条链连续积累）。

### 比较的方法
- **六种存储变体**：
  - 无存储（Closed-book）
  - 分块检索（Chunk retrieval）：将对话按块切分，BM25检索后返回Top-3整块
  - 逐字转储（Verbatim dump）：将会话原样存储为文件
  - 折叠会话（Foldered sessions）：在逐字转储基础上由LLM设计文件夹分类，文件内容不变
  - 重组存储（Reorganized store）：由LLM对逐字转储进行重组，含保留版（preserve）和压缩版（condense）
  - 智能体策管存储（Agent-curated store）：管理智能体从空存储开始逐块构建
- **技能场景额外变体**：
  - 无存储
  - 情节日志（Episode log）：逐字追加每次执行轨迹
  - 策管技能（Curated skills）：管理智能体蒸馏为技能文件
  - 策管技能+记忆笔记（Curated skills+mem）：增加记忆笔记，并加上严格输出门
  - 策管技能+记忆笔记+指导合成（Curated skills+mem (GS)）：搜索智能体检索后合成自定义指导文本

### 控制变量与测量
- **固定变量**：管理智能体和搜索智能体默认使用gpt-5.4-mini（高推理努力），执行智能体在技能场景固定为gpt-4.1或gpt-4.1-mini。
- **变化轴**：存储构建方式、流规模、工具集、管理/搜索智能体模型能力。
- **测量指标**：
  - 答案质量：正确率和归因率（由单独裁判模型评判，PersonaMem用精确匹配）
  - 成本：每查询的token数、工具轮次、按实际API价格计算的美分
  - 存储健康：文件/文件夹/节数量、二叉树指标（深度、扇出、内容距离相关性等）、内容泄漏、交叉引用数

- **潜在不足**：
  - PersonaMem 32k和128k层级的对话内容不同，跨层级比较只能提供粗略规模趋势。
  - 每个对话基准只有一个代表性对话（LoCoMo一个conv-50，REALTALK一个chat，PersonaMem 128k一个），可能受单条对话特性影响。
  - 技能场景中，策管条件消耗的计算成本显著高于无存储或情节日志，但这些成本在“资源”部分以美分形式公平报告。
  - 部分实验（如能力网格）的统计显著性基于单条42条问题的对话，差异较小，作者自己标注“suggestive而非settled”。

## 6. 论文的主要结论与发现

### RQ1: 管理智能体构建什么样的存储结构？
- 管理智能体构建主题树，但**形态更多是模型的签名而非对规模的响应**：规模增大时存储合并而非分散，层次从文件夹/文件向文件内标题迁移。
- **文件名、文件夹、标题三级层次的使用因模型而异**：弱模型（nano）产生大而浅的森林，强模型（gpt-5.4）产生深树并大量使用交叉引用，中间模型（mini）将几乎全部结构放在文件内标题中。
- **最明显的退化行为**：重组时管理智能体默认会隐式压缩内容，除非有明确的“保留每个事实”规则。

### RQ2: 存储形状对检索的影响
- **没有一种形状在所有情况下都胜出**：折叠会话（Foldered sessions）在多个基准上最稳定领先，但策管存储在LoCoMo上领先，在PersonaMem 32k上却最差。
- **组织的明确收益是搜索成本**：当原始材料很大时，有组织存储的检索成本约减半（PersonaMem上从4.0美分降至1.4美分）。
- **技能场景中，赢家取决于执行智能体的强度**：强执行智能体（gpt-4.1）下逐字情节日志最好（87.1%），弱执行智能体（gpt-4.1-mini）下指导合成（GS）最好（76.4%），且GS是部署成本最便宜的存储。

### RQ3: 骨干模型能力的影响
- **对话场景**：管理智能体的能力主要体现在组织风格上，而非答案质量上（三个管理智能体产生的存储形状差异极大，但正确率在66.7-73.8%小范围内波动）。搜索智能体的能力则直接贴现在答案质量上（正确率从约62%升至79%）。
- **技能场景**：管理智能体能力表现为**阈值**——弱模型（nano, mini）之间质量持平，强模型（gpt-5.4）大幅提升（+13个百分点），且其存储的蒸馏质量比数量更重要。

### RQ4: 随着规模增长的可持续性
- **存储变得更有用**：全链中所有存储变体从早期到后期性能提升，弱执行智能体获益最大（情节日志从51.4%升至91.4%，无效动作率从40%降至24%）。
- **早期记忆存活**：大多数早期文件在链末被编辑而非删除，更强管理智能体表现为更广泛而在位编辑而非替代。
- **组织性侵蚀**：多数存储随增长丧失组织合同遵循度，仅gpt-5.4管理智能体能保持基本不变。
- **成本分割**：策管存储保持每任务成本稳定，每查询成本平坦；逐字情节日志的“全量服务”检索成本随存储大小线性增长。

### RQ5: 工具集的影响
- **工具集本身可以显著改变存储形态**（同模型下文件数可能差两个数量级），但**对答案质量的改变很小**（LoCoMo上三种工具集86.1-86.7%，差异在单次运行变化范围内）。
- 在技能场景中，Shell工具集产生了最好的结果，因为其写操作更自然，产生了更紧凑的存储。
- **工具集不是中性的包装器**：它可以直接改变存储的组织方式和随后的检索成本。

## 7. 优点

- **系统性首次探索**：首次对文件系统记忆的默认假设进行受控实验研究，填补了学术空白。
- **形式化框架**：提出管理/搜索/执行三角色分解以及统一的存储定义，便于后续研究复用。
- **多维度覆盖**：同时考察对话记忆和程序记忆，变化存储构建方式、规模、工具集、模型能力等四个主要变量，实验设计全面。
- **精细的成本与健康度量**：不仅报告答案质量，还详细报告每查询token消耗、工具轮次、API价格、以及存储的树形结构指标（深度、扇出、内容距离相关性等），提供了丰富的诊断信息。
- **增长轨迹分析**：在技能场景中按任务索引记录存储大小、事件、成本、成功率的演进，揭示了可持续性的动态模式。
- **工具集作为设计杠杆**：发现仅改变工具集就能产生与更换模型相当的组织变化，这提供了实用指导：开发者可以通过调整工具集来诱导目标存储形态。
- **公平性控制**：固定裁判模型、统一搜索提示云、修复提示缺陷后重新运行、报告单次运行变化。

## 8. 不足与局限

- **规模局限**：所有对话实验最长128k token（约20个会话），技能场景最长140个任务。真正的长期记忆（数月、千级别任务）的增长行为仍未知。
- **基准覆盖有限**：每个对话基准仅使用1条具体对话（LoCoMo一个conv-50，REALTALK一个chat），结论可能受对话特性影响。
- **单次运行变化**：管理智能体构建的存储形状在不同运行间可能有显著变化（如文件数从2变到29），作者承认这一点，但总体趋势仍稳健。
- **模型能力阶梯不完整**：对话场景中能力阶梯只做了一种规模（128k），未覆盖更小规模下管理智能体的收益（如PersonaMem 32k上提升管理智能体确实提高了答案质量）。
- **裁判模型依赖**：所有评判使用gpt-5.4-mini，可能引入偏差；裁判对PersonaMem使用精确匹配避免了这种偏差。
- **技能场景的管道复杂性**：策管条件的构建成本显著高于无存储或情节日志，但论文未提供“净收益”视角（如每解决一个任务的总成本比较），但表16提供了分解数据。
- **工具集研究的清洁性**：重新运行后发现原始提示有措辞缺陷，虽然行为影响可忽略后重新运行，但表明工具集变体对提示措辞敏感。
- **未探索更大模型**：所有实验使用商业API模型，未探索开放权重模型或自定义微调模型。
- **未讨论多用户/多会话并发情况**：现实部署中多个用户或智能体可能共享或并发访问同一文件存储，本文场景均为单会话顺序访问。
